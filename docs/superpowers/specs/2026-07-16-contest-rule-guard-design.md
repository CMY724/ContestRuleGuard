# ContestRuleGuard（赛规通）设计规格

状态：已由参赛者确认，等待书面规格复核  
日期：2026-07-16  
目标赛题：算法创新赛——AI+OPC创新创业  
目标：通过校赛并以全国总决赛获奖为质量标准推进

## 1. 项目摘要

ContestRuleGuard 的中文作品名为“赛规通：证据图驱动的竞赛合规智能体”。它面向需要阅读多份竞赛通知、整理时间节点并准备参赛材料的个人参赛者，将自然语言规则转换为带有原文证据、可追溯且可执行的合规检查规则。

产品不以聊天问答为核心，而以“规则导入—结构化理解—冲突分析—材料检查—报告导出”为完整闭环。系统的主要技术命题是：能否将分散在 PDF、Word、PPT 和图片中的自然语言竞赛要求，可靠地编译成可以自动执行的检查器，并证明其优于直接调用大模型。

## 2. 背景与约束

### 2.1 参赛约束

- 参赛者为人工智能专业本科生，采用单人 OPC 模式。
- 每周可稳定投入 10–15 小时。
- 开发预算为 0–500 元，不含后续比赛报名费用。
- 可邀请 10–20 名同学参与真实访谈和试用，但产品构思、研发、生产与交付均由参赛者独立完成。
- 校赛提交截止时间为 2026-09-25 17:00。
- 校赛材料至少包括作品说明文档、答辩 PPT 和可运行 Demo。
- 校赛、省赛和国赛的成员及顺序必须一致。
- 作品材料需要满足匿名评审要求，不能出现学校名称、学校 Logo 或指导教师等身份信息。

### 2.2 产品约束

- 第一版必须在校赛截止前形成完整可演示产品，不能以概念原型代替核心功能。
- 关键判断必须能返回原文证据；没有证据时只能提示人工核实，不能判定违规。
- 大模型负责语言理解，确定性程序负责可计算规则，避免所有判断都依赖生成式模型。
- 原始材料、API 密钥、个人信息和未脱敏问卷不能进入公开仓库。
- 产品需要支持低成本部署，并允许切换 OpenAI 兼容的模型供应商。

## 3. 用户与问题

### 3.1 目标用户

第一目标用户是参加高校学科竞赛的个人学生。其典型任务包括：

1. 从官网、学校和赛区发布的多份通知中提取报名资格、时间、材料和费用。
2. 判断校赛、省赛和国赛规则分别适用于哪个阶段。
3. 发现新旧通知之间的变更或冲突。
4. 在提交前检查作品说明、PPT、代码包和 Demo 是否完整合规。
5. 保存一份可以解释每个判断依据的检查报告。

### 3.2 核心痛点

- 通知来源分散，规则经常藏在附件、表格、图片或后续补充通知中。
- 一般通知、赛题规则和校内要求的适用范围不同，人工容易混淆。
- 文件大小、页数、视频时长、成员顺序和匿名信息等细节容易漏检。
- 普通大模型能够总结通知，但可能遗漏条件、混淆来源或生成没有证据的答案。
- 参赛者通常只在截止前集中检查材料，发现问题后缺少修改时间。

## 4. 产品定位与成功标准

### 4.1 定位

ContestRuleGuard 是“竞赛规则编译与材料合规检查系统”，不是通用聊天机器人、竞赛资讯平台或自动报名工具。

### 4.2 校赛版成功标准

- 支持 PDF、Word、PPT 和图片通知的文本与版面解析。
- 支持时间、资格、团队、材料、格式、匿名、阶段关系和冲突八类规则。
- 每条结构化规则包含来源文件、页码或页面、原文片段、适用范围与置信度。
- ContestRule DSL 可以编译并执行常见确定性规则。
- RuleGraph 可以保留新旧规则、来源层级、补充、覆盖和冲突关系。
- 材料检查支持作品说明、PPT/PDF、代码包清单和 Demo 基础属性。
- 系统可以输出通过、警告、阻断三级风险及可追溯报告。
- 提供 Docker 化运行方式和可供用户测试的演示版本。

### 4.3 实验门槛

下列数值是进入校赛提交版本的目标门槛，不是预先承诺的结果；所有最终数值必须来自真实实验：

- 规则抽取 F1 目标不低于 0.85。
- 证据页码或页面定位准确率目标不低于 0.95。
- 确定性违规检查 F1 目标不低于 0.95。
- 冲突检测 F1 目标不低于 0.85。
- 相比直接大模型问答，完整系统的错误率目标降低 30% 以上。
- 用户完成材料检查的时间目标缩短 50% 以上。
- 10–20 名试用者的系统可用性量表目标不低于 75/100。
- 单个竞赛项目的平均模型调用成本目标控制在约 1 元以内。

## 5. 非目标

校赛版不实现以下功能：

- 通用知识聊天或开放领域问答。
- 全网自动爬取竞赛信息。
- 手机原生 App。
- 复杂的账户、组织、团队协作和支付系统。
- 向学校或比赛官网自动提交材料。
- 对 Demo 视频进行逐帧语义理解。
- 自研或从头训练大语言模型。
- Neo4j、分布式任务队列等超出当前规模的基础设施。

## 6. 用户流程

1. 用户创建一个竞赛项目并填写项目名称、赛道和目标阶段。
2. 用户上传官网通知、赛题规则、校内通知和补充文件，并指定来源级别。
3. 系统解析文本、版面、表格与图片 OCR 结果，生成候选证据片段。
4. 结构化抽取器生成 ContestRule，证据验证器检查字段与原文是否一致。
5. 系统在规则中心展示规则卡片；低置信度结果必须由用户确认。
6. RuleGraph 合并已确认规则，识别补充、覆盖、冲突和阶段关系。
7. 系统生成时间线、材料清单和待核实事项。
8. 用户上传作品说明、PPT/PDF、代码清单和 Demo。
9. 确定性引擎与语义引擎分别执行检查，聚合为风险清单。
10. 用户修改材料并重复检查，直至不存在阻断项。
11. 系统导出带证据的 HTML/PDF 合规报告。

## 7. 界面与功能边界

### 7.1 项目首页

展示截止倒计时、材料完成度、阻断风险、待确认规则、最近检查结果和下一步行动。

### 7.2 规则中心

以卡片方式展示规则类型、结构化值、适用赛道与阶段、来源、证据、时间和置信度。用户可以确认、纠正或标记为不适用，所有更改进入审计记录。

### 7.3 冲突中心

并排展示冲突规则的来源、日期、适用范围和系统优先级建议。系统不得静默删除旧规则，也不得在证据不足时自动覆盖。

### 7.4 材料检查

确定性检查包括：

- 文件扩展名、大小、页数、命名和数量。
- 视频时长与可读取性。
- 项目名称、成员姓名与顺序的一致性。
- 学校名称、指导教师和其他匿名评审敏感文字。
- 必需章节、文件或链接是否存在。

语义检查包括：

- 作品说明是否覆盖背景、技术、创新、应用价值和后续计划。
- PPT 是否与作品说明中的核心功能、指标和结论一致。
- 商业计划是否覆盖市场、产品、运营、营销和财务等 OPC 评分维度。
- Demo 的语音转写或脚本是否覆盖核心产品流程。
- 材料中的事实、指标与系统功能是否存在明显矛盾。

### 7.5 报告中心

按照“通过、警告、阻断”三级输出问题。每个问题必须包含：规则、证据、被检查位置、风险解释、置信度和修改建议。报告可导出为 HTML 和 PDF。

## 8. 技术架构

### 8.1 总体架构

- 前端：React + TypeScript。
- 后端：Python + FastAPI。
- 数据库：SQLite；数据模型保持可迁移到 PostgreSQL。
- PDF：PyMuPDF。
- Word：python-docx。
- PPT：python-pptx。
- 图片与扫描件：中文 OCR 作为文本解析失败时的兜底。
- 视频：FFmpeg 读取基础属性；语音转写为可选增强。
- RuleGraph：Python 领域模型与图算法，SQLite 持久化。
- AI：OpenAI 兼容接口，通过环境变量配置供应商、模型和密钥。
- 部署：Docker；开发阶段本地运行，测试阶段提供公开演示地址。

### 8.2 模块边界

1. `ingestion`：文件接收、类型识别、解析与页面级标准化。
2. `evidence`：证据片段切分、位置记录、检索与引用。
3. `contest_rule`：DSL 数据模型、结构验证和编译器。
4. `rule_graph`：规则归并、时序关系、来源优先级与冲突检测。
5. `audit_hard`：确定性文件、字段和一致性检查。
6. `audit_semantic`：只处理不能可靠编译的语义性规则。
7. `verification`：低置信度二次验证、证据一致性和风险校准。
8. `reporting`：风险聚合、审计记录及 HTML/PDF 报告。
9. `web`：项目、规则、冲突、材料与报告界面。

每个模块通过显式数据结构通信，避免解析、模型调用、图逻辑和页面代码互相耦合。

## 9. 核心算法设计

### 9.1 核心创新：证据约束规则编译

系统先从原始通知中定位候选证据，再生成类型明确的 ContestRule。每个字段都必须绑定来源证据。输出通过 JSON Schema 或等价结构验证后进入编译器；非法、缺证据或冲突字段不能直接执行。

ContestRule 的首批规则类型包括：

- `DEADLINE`：动作、时间、时区、阶段与适用对象。
- `ELIGIBILITY`：身份、学历、地区、学校或赛题条件。
- `TEAM_SIZE`：最小/最大人数、是否要求单人、是否允许跨校。
- `FILE_REQUIRED`：材料类型、数量、是否必需和适用阶段。
- `FILE_CONSTRAINT`：格式、大小、页数、时长和命名。
- `CONSISTENCY`：跨材料或跨阶段必须一致的字段。
- `ANONYMITY`：禁止出现的身份、文字、Logo 或元数据。
- `DEPENDENCY`：某项任务依赖另一项任务或前置条件。

编译器将规则转换为统一检查接口。能够确定计算的规则生成硬检查器；无法确定编译的规则进入语义检查队列并保留人工确认入口。

### 9.2 支撑创新：时序证据 RuleGraph

图节点至少包括文档、证据、规则、阶段、材料、动作和风险。边至少包括：

- `SUPPORTED_BY`：规则由证据支持。
- `APPLIES_TO`：规则适用于阶段、赛道或材料。
- `SUPPLEMENTS`：新规则补充旧规则。
- `OVERRIDES`：更具体或更高优先级规则覆盖一般规则。
- `CONFLICTS_WITH`：两条规则不能同时满足。
- `DEPENDS_ON`：行动存在前置依赖。
- `SUPERSEDES`：后续通知替代旧通知。

默认优先级仅作为建议：更具体的赛题/校内要求优先于一般通知，后发布的有效补充通知优先于旧通知。系统必须展示推理链并允许人工确认，不能把优先级当成不可解释的黑盒规则。

### 9.3 支撑创新：自适应混合审查

- 高置信度且可编译的规则直接执行确定性检查。
- 低置信度结构化结果触发第二轮证据验证。
- 语义规则只对相关证据和材料片段调用模型，不发送整套材料。
- 内容指纹与结果缓存避免重复调用。
- 风险分数综合违规严重度、判断置信度和截止紧迫度。
- 模型调用失败时，硬检查仍然完成，语义结果标记为待重试。

## 10. 数据与评测

### 10.1 数据集

- 收集约 30 份可公开使用的竞赛通知及附件。
- 建立至少 200 条结构化规则与证据标注。
- 覆盖时间、资格、团队、材料、格式、匿名、阶段关系和冲突八类规则。
- 20 份用于开发和提示词调整，10 份作为隐藏测试集。
- 用户自行完成金标准标注，邀请试用者仅做随机抽样复核和产品体验，不参与核心研发。
- 仓库只保存可公开的文档、链接、脱敏文本或派生标注。

### 10.2 基线与消融

比较三种方法：

1. 直接大模型问答。
2. 大模型结构化输出 + ContestRule 编译器。
3. 完整系统：编译器 + RuleGraph + 二次验证。

主要指标包括规则抽取 Precision/Recall/F1、证据定位准确率、冲突检出率、违规检查 Precision/Recall/F1、误报率、延迟、模型成本和证据支持率。

### 10.3 用户研究

- 招募 10–20 名高校竞赛参与者。
- 使用相同材料比较人工检查和系统辅助检查的完成时间、遗漏数和正确率。
- 收集系统可用性量表、功能满意度、付费意愿和开放反馈。
- 参与者自愿同意，结果匿名统计；原始身份信息不进入公开仓库。

## 11. 异常处理与安全

- OCR 置信度不足：标记原图区域，要求用户确认。
- 文件加密或不支持：指出文件、失败原因和可执行处理方法。
- 规则字段缺证据：拒绝生成确定结论。
- 两条规则冲突：同时保留，展示来源、时间和建议优先级。
- 模型不可用：继续运行硬检查，语义检查进入可重试状态。
- 报告生成失败：保留检查结果，允许重新导出。
- 用户删除项目：删除原始材料和派生内容，不将其用于其他模型训练。
- 所有密钥仅从环境变量读取；日志不得写入密钥、完整身份证明或原始问卷。

## 12. 商业模式

第一阶段验证以下假设，不在校赛前开发支付：

- 免费版：创建 1 个项目并执行基础检查。
- 单次版：按竞赛项目收费 9.9–19.9 元。
- 个人会员：多项目、历史版本对比和高级报告。
- 高校版：通知结构化发布、规则模板和批量材料预检。

用户研究需要验证目标用户是否愿意付费、可接受价格以及最有价值的功能。财务预测必须基于明确假设和真实调研，不编造收入或合作证明。

## 16. 材料制作与质量保证

- 技术架构图、方法图和实验结果图在内容稳定后设计，避免用概念图代替真实数据。
- 答辩 PPT 使用 Presentations 技能构建；在导出前逐页渲染检查重叠、溢出、断行、图表数据和匿名信息。
- 作品说明文档使用适合的文档技能制作并进行版式核验。

## 17. 主要风险与缓解措施

| 风险 | 缓解措施 |
| --- | --- |
| 功能过多导致无法按期完成 | 按“必须、有余量、国赛增强”三级优先级执行 |
| 被认为是大模型套壳 | 以 ContestRule 编译器、RuleGraph、消融实验为主线 |
| 规则抽取幻觉 | 字段级证据绑定、结构验证、二次验证和人工确认 |
| 公开仓库泄露身份或密钥 | 匿名提交策略、no-reply 邮箱、gitignore 和发布前扫描 |
| 评测集过小或调参泄漏 | 固定开发/隐藏测试划分，保留原始评测记录 |
| 用户调研证据不足 | 及早招募 10–20 名目标用户并保存匿名统计 |
| 模型费用超预算 | 相关片段调用、缓存、低置信度才二次验证、供应商可切换 |
| Demo 依赖网络不稳定 | 提供本地 Docker 运行和可复现示例项目 |
